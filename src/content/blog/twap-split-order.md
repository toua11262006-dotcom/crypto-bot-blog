バックテストでは想定通りの価格で約定していたのに、本番で実際に発注すると思ったより悪い価格で約定してしまう。発注サイズが大きくなってくると、こうした悩みに直面しやすくなります。原因の一つが「板の薄い部分まで一気に食ってしまう」ことです。この記事では、注文を時間的に分割して発注する**TWAP(Time-Weighted Average Price)**の考え方と、Pythonでの基本的な実装パターンを整理します。

## TWAPとは何か

TWAPは「一定時間にわたって注文を均等に分割し、時間を分散させながら約定させていく」発注手法です。例えば1 BTCを買いたい場合、1回で1 BTC分の成行注文を出すのではなく、「0.1 BTCを10回に分けて、5分おきに発注する」といった形で約定させます。

名前の由来は「時間加重平均価格」で、分割した各注文の約定価格を均して見たときに、ある時間帯の平均的な価格に近づけることを狙う手法だからです。対して、出来高の多い時間帯に多めに発注する手法はVWAP(出来高加重平均価格)と呼ばれ、考え方は似ていますが基準が「時間」か「出来高」かで異なります。

## なぜ分割発注でスリッページを抑えられるのか

[板情報(オーダーブック)の記事](/blog/orderbook-basics/)で触れた通り、注文は板に並んでいる価格を上から(買いなら安い方から)食っていく形で約定します。板が薄い状態で大きな成行注文を一気に出すと、1件目の注文だけでも何段も価格が動いてしまい、約定価格が大きく悪化することがあります。これが[スリッページの記事](/blog/slippage-thin-orderbook/)で解説した、板の厚みに起因するスリッページです。

注文を分割すると、1回あたりの注文サイズが小さくなるため、板の浅い部分だけで約定しやすくなります。さらに発注のタイミングを分散させることで、他の参加者の注文と混ざり合いながら約定していくため、特定の瞬間の板の薄さに資金を一気にぶつけるリスクも下がります。もちろん、分割したからといって約定価格が改善する保証はありません。市場全体が一方向に動いている最中は、分割しても平均的に不利な価格を拾ってしまうこともあります。[取引コストが成績に与える影響の記事](/blog/trading-cost-impact-formula/)で整理した通り、スリッページはあくまで「確率的に抑えられるコスト」として捉えるのが実務的です。

## シンプルなTWAP実装

以下は、ccxtを使って総量を等分割し、一定間隔で成行注文を出していく最小限のTWAP実装の例です。ccxtの基本的な使い方は[ccxt入門の記事](/blog/ccxt-python-tutorial/)を参照してください。

```python
import time
import ccxt

def execute_twap(exchange, symbol, side, total_amount, slices, interval_sec):
    """
    total_amount を slices 回に等分割し、interval_sec 秒おきに成行発注する
    """
    chunk = round(total_amount / slices, 8)
    filled_orders = []

    for i in range(slices):
        # 最後のチャンクは誤差を吸収するため残り全量にする
        amount = total_amount - chunk * (slices - 1) if i == slices - 1 else chunk

        order = exchange.create_order(
            symbol=symbol,
            type='market',
            side=side,
            amount=amount,
        )
        filled_orders.append(order)
        print(f'[{i + 1}/{slices}] {side} {amount} {symbol} 発注完了')

        if i < slices - 1:
            time.sleep(interval_sec)

    return filled_orders


exchange = ccxt.mexc({
    'apiKey': 'YOUR_API_KEY',
    'secret': 'YOUR_SECRET',
})

execute_twap(exchange, 'BTC/USDT', 'buy', total_amount=0.5, slices=10, interval_sec=30)
```

この例は仕組みを理解するための最小限の実装です。実運用に組み込む場合は、少なくとも次の点を加える必要があります。

- **数量・価格の精度調整**: 等分割した数量が取引所の最小発注単位や精度の刻みに合っているか確認する処理が必要です。[注文の最小単位(ロットサイズ)の記事](/blog/order-precision-lot-size/)を参照してください
- **発注エラー時のリトライ・中断判断**: 途中の1回が失敗したときに、残りをどう扱うか(スキップ・リトライ・全体中断)を決めておく
- **レートリミットへの配慮**: 分割数が多い・間隔が短いほどAPI呼び出し頻度が上がります。[APIレートリミットの記事](/blog/api-rate-limit-design/)も合わせて確認してください
- **約定状況のログ記録**: 各チャンクの約定価格・数量を記録し、後から平均約定価格を検証できるようにしておく

## 指値ベースのTWAPという選択肢

上記の例は成行注文を使っていますが、各チャンクを指値(リミット)で出し、一定時間内に約定しなければキャンセルして次のチャンクに進む、という設計も考えられます。指値には「板を厚くする側(メイカー)」として手数料が有利になる可能性がある一方、「約定しない」リスクも生じます。指値・成行それぞれの特徴は[注文タイプの入門記事](/blog/order-types-guide/)で整理しているので、どちらが戦略に合うかはそちらも参考にしてください。

## TWAPが万能ではない理由

分割発注は板の薄さに起因するスリッページを緩和する手法であり、以下のような場面では効果が限定的、あるいは逆に不利になることがあります。

- **価格が一方向に強く動いている局面**: 分割して時間をかけるほど、不利な方向への価格変動を全体として多く拾ってしまう可能性があります
- **分割しすぎによる機会損失**: 間隔を長くしすぎると、約定が完了する前に相場環境が変わってしまうことがあります
- **取引所によってはTWAP注文タイプを標準機能として提供している場合もある**: その場合は自前のループより取引所側の機能を使う方が安定することもあります。対応状況や挙動の詳細は変更されることがあるため、必ず利用する取引所の公式ドキュメントで確認してください

## まとめ

- TWAPは注文を時間的に分割して発注し、特定の瞬間の板の薄さに資金を一気にぶつけるリスクを減らす手法
- 板が薄いほど1回の大口注文によるスリッページが大きくなりやすく、分割によってその影響を緩和しやすくなる
- 実装では等分割した数量をそのままループで発注するだけでなく、精度調整・エラー処理・レートリミット・ログ記録まで含めて設計する必要がある
- 成行だけでなく指値ベースで分割する設計も選択肢になる
- 分割すれば必ず有利な価格になるわけではなく、トレンドが強い局面では効果が限定的になることもある

分割発注はあくまで「板の薄さによる不利を減らす」ための工夫であり、相場の方向そのものを予測するものではありません。導入する場合も、まずは[ペーパートレードの記事](/blog/paper-trading-guide/)で紹介した検証環境で挙動を確認してから本番に組み込むことをおすすめします。
