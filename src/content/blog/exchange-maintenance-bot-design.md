多くの取引所は、システムの更新や安定性向上のために定期的なメンテナンスを行います。メンテナンス自体は珍しいことではありませんが、その間にボットがどう動くかを考えていないと、注文が失敗したまま気づかない、といった事態につながります。この記事では、取引所のメンテナンスで何が起きるのか、ボット側でどう備えればよいのかを一般論として整理します。

## メンテナンスには種類がある

取引所のメンテナンスは、大きく分けるといくつかのパターンがあります。

- **定期メンテナンス**: あらかじめ日時が告知される、システム更新のためのもの
- **緊急メンテナンス**: 障害や不具合への対応として、予告なく行われるもの
- **ネットワーク(ブロックチェーン)側のメンテナンス**: 入出金のみ一時停止するなど、取引自体には影響しない場合もある

このうち、ボット運用者が最も注意すべきなのは前者2つです。障害によるダウンの話は[取引所がダウンした時のフェイルセーフ設計の記事](/blog/exchange-outage-failsafe/)で扱っていますが、今回はメンテナンス、特に「予告された停止」にどう向き合うかに焦点を当てます。

## メンテナンス中に起こりうること

メンテナンス中、取引所のAPIは通常の挙動と異なる応答を返すことがあります。想定しておきたい代表的なパターンは次の通りです。

| 状況 | ボットから見た症状 |
| --- | --- |
| APIサーバー自体が停止 | タイムアウト、接続エラーが連続する |
| メンテナンス専用のレスポンス | 通常と異なるエラーコード・メッセージが返る |
| 発注APIのみ制限 | 残高取得などは成功するが、注文だけ失敗する |
| WebSocketの切断 | リアルタイム配信が止まり、再接続もできない |

特に厄介なのは「APIは一応応答するが、注文は常に失敗する」ケースです。単純なネットワークエラーと区別がつきにくく、[再起動時の状態復元の記事](/blog/bot-restart-state-recovery/)で触れたような二重発注のリスクにもつながりかねません。

## ccxtでのメンテナンス検知

Pythonでccxtを使っている場合、メンテナンス関連のエラーは例外として区別できるように用意されています。ccxtの例外階層には`ExchangeNotAvailable`があり、さらにその一種として`OnMaintenance`という専用の例外クラスが存在します。取引所がメンテナンス中であることをAPIレスポンスから検出できた場合、ccxt側がこの例外に変換してくれる仕組みです。

```python
import ccxt

exchange = ccxt.mexc({
    "apiKey": "YOUR_API_KEY",
    "secret": "YOUR_SECRET",
})

try:
    order = exchange.create_order("BTC/USDT", "limit", "buy", 0.001, 30000)
except ccxt.OnMaintenance as e:
    logger.warning(f"メンテナンス中のため発注を見送りました: {e}")
except ccxt.ExchangeNotAvailable as e:
    logger.warning(f"取引所に接続できません: {e}")
except ccxt.NetworkError as e:
    logger.warning(f"ネットワークエラー: {e}")
```

ただし、どの例外クラスに分類されるかは取引所のレスポンス仕様に依存します。必ずしも`OnMaintenance`できれいに判定できるとは限らないため、「想定外のエラーが続いたら一旦停止する」という後述のフェイルセーフも併せて用意しておくと安心です。この点は[取引所のAPI仕様変更への備えの記事](/blog/exchange-api-spec-change/)で解説した考え方とも共通しています。

## ボット側で備えておきたい設計

### 1. メンテナンス予定の事前確認を仕組みに入れる

定期メンテナンスは多くの場合、取引所の公式サイトやステータスページ、公式SNSで事前に告知されます。これを人力で毎回確認するのは現実的ではないため、取引所がメンテナンス情報をAPIで公開している場合は、起動時やループの中で定期的にチェックする設計が考えられます。公開APIがない場合でも、「メンテナンス時間帯だけ新規発注を控える」といったスケジュールをボットの設定に持たせておくだけでも効果があります。

### 2. エラーの連続回数で自動停止する

メンテナンス中かどうかの判定が難しい場合でも、「同じエラーが一定回数以上続いたら新規注文を止める」というロジックは実装しやすく、効果も大きいです。どのタイミングでボットを止めるべきかについては[ボットを止めるべきタイミングの記事](/blog/bot-stop-criteria/)でも詳しく整理しています。

### 3. 検知したら必ず通知する

メンテナンスによる発注停止を、ログに記録するだけで済ませてしまうと、再開に気づかず長時間ポジションを持てないまま放置する、といった事態になりかねません。[Discordへの通知の仕組み](/blog/discord-notification-bot/)などを使って、「メンテナンスを検知して発注を停止した」こと自体を即座に知らせる設計にしておくと安心です。

### 4. 本番前にメンテナンス時の挙動を想定したテストをしておく

実際のメンテナンス中にしか再現できない挙動も多いため、事前に完全にテストするのは難しい部分です。それでも、[サンドボックス(テストネット)環境](/blog/exchange-sandbox-testnet/)でAPIキーを無効にしたり、意図的に接続を切ったりして、例外処理が正しく動くかを確認しておくことは可能です。想定外のエラーでボットが異常終了しない、少なくとも「安全に止まる」ことだけは事前に確認しておきたいポイントです。

## まとめ

- 取引所のメンテナンスには定期・緊急・ネットワーク側など複数のパターンがある
- メンテナンス中はAPIが通常と異なる挙動を示し、注文だけが失敗することもある
- ccxtには`OnMaintenance`などの例外クラスがあるが、判定できない場合のフェイルセーフも必要
- エラーの連続回数での自動停止と、検知時の即時通知をセットで用意しておく
- 本番前に、例外処理が「安全に止まる」ことを確認しておく

※取引所のメンテナンス仕様やAPIのエラー形式は変更されることがあるため、実装時には必ず各取引所の公式ドキュメントで最新情報を確認してください。
