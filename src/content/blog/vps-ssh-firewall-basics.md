自動売買ボットを動かすためにVPSを契約した直後は、取引所のAPIキー設定や[ボットの常時稼働の設定](/blog/vps-bot-24h/)に目が向きがちで、VPS自体の「OS層のセキュリティ」は後回しになりやすいところです。しかしVPSはボットが動いているあいだ中、インターネットに向けて22番ポート(SSH)を開けたまま稼働し続けています。この記事では、最初に設定しておきたいSSH鍵認証とファイアウォールの基本的な考え方を一般的な技術解説として整理します。

## なぜVPSのOS層セキュリティが重要なのか

取引ボット向けのVPSセキュリティを考えるとき、見るべき対象は大きく2種類に分かれます。

- **取引所のAPIキー**: [APIキーの安全な管理方法](/blog/api-key-security/)で扱っているように、出金権限を外す・IP制限をかけるといった対策が中心
- **VPS自体へのログイン**: SSH経由でサーバーに侵入されると、APIキーの管理方法に関わらず、保存されている設定ファイルや秘密情報をまとめて読み取られる

つまりAPIキーをどれだけ厳重に管理していても、VPSへのSSHログインが総当たり攻撃で破られれば、その対策ごと無効化されてしまう可能性があります。インターネット上の22番ポートは、契約した瞬間から無差別の自動スキャンやログイン試行の対象になると言われています。ボットを動かすVPSに限らず、インターネットに公開されたサーバー全般に当てはまる前提として覚えておく必要があります。

## パスワード認証の限界とSSH鍵認証への切り替え

多くのVPSは契約直後、パスワードでSSHログインできる状態になっています。パスワード認証には次のような弱点があります。

- 総当たり攻撃(ブルートフォース)で突破される可能性がある
- 使い回しているパスワードが他サービスの漏洩と連動して悪用されるリスクがある
- ログイン試行のたびにパスワードを入力・管理する手間がある

これに対してSSH鍵認証は、秘密鍵と公開鍵のペアを使う方式です。秘密鍵は自分のPC側に置いたままにし、VPS側には公開鍵だけを登録します。パスワードのように「推測して当てる」ことが実質的にできないため、総当たり攻撃への耐性が大きく高まります。

### 鍵ペアの作成と登録

自分のPC(クライアント側)で鍵ペアを作成します。

```bash
# ed25519形式の鍵ペアを作成(RSAより鍵長が短く高速)
ssh-keygen -t ed25519 -C "trading-bot-vps"
```

作成した公開鍵をVPSに登録するには`ssh-copy-id`が便利です。

```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub user@your-vps-ip
```

鍵認証でログインできることを確認したら、VPS側の`/etc/ssh/sshd_config`を編集してパスワード認証を無効化します。

```
PasswordAuthentication no
PermitRootLogin no
PubkeyAuthentication yes
```

設定後はSSHを再起動します。

```bash
sudo systemctl restart sshd
```

**注意**: `PasswordAuthentication no`にする前に、必ず鍵認証でログインできることを別のターミナルで確認してください。設定ミスのまま既存セッションを切断すると、パスワードでもログインできずサーバーにアクセスできなくなる事故につながります。

### 秘密鍵ファイルのパーミッション

秘密鍵はクライアント側のファイルですが、パーミッションが緩いと`ssh`コマンド自体が警告を出して拒否することがあります。

```bash
chmod 600 ~/.ssh/id_ed25519
```

秘密鍵を複数人で共有したり、クラウドストレージに無防備に置いたりしないことも基本的な注意点です。

## ファイアウォールで不要なポートを塞ぐ

SSHログインの安全性を上げても、VPS上で動いている他のサービスが外部に無防備に公開されていれば攻撃の入口になります。Ubuntu系のディストリビューションであれば`ufw`(Uncomplicated Firewall)で最小限のポートだけを開ける設定が一般的です。

```bash
# デフォルトで受信はすべて拒否、送信は許可
sudo ufw default deny incoming
sudo ufw default allow outgoing

# SSHだけ許可する(ポート番号は環境に合わせる)
sudo ufw allow 22/tcp

# 設定を有効化
sudo ufw enable

# 現在のルールを確認
sudo ufw status verbose
```

ボット自体は取引所のAPIに対して自分から通信を発信するだけで、外部からの着信を受け付ける必要がないケースが多いはずです。その場合、開けるポートはSSH(必要であれば監視用のダッシュボードなど)だけに絞り、それ以外は閉じておくのが基本の考え方になります。

### SSHポート番号の変更について

SSHのポート番号を22番から別の番号に変更すると、無差別スキャンによるログイン試行の「ノイズ」を減らせることがあります。ただし、これはあくまで目に見えるログを減らす効果が中心で、ポート番号を知っている相手からの標的型の攻撃には無力です。鍵認証やファイアウォールといった本質的な対策を省略する理由にはならない点に注意してください。

## fail2banで総当たり攻撃の試行を遮断する

鍵認証に切り替えたあとも、パスワード認証を試みる自動化されたログイン試行自体は届き続けます。`fail2ban`は、一定回数ログインに失敗したIPアドレスを自動的に一時ブロックする仕組みで、多くのディストリビューションでパッケージとして提供されています。

```bash
sudo apt install fail2ban
sudo systemctl enable --now fail2ban
```

デフォルトの設定でもSSHへの総当たりを検知してブロックする挙動が含まれていることが多いですが、詳細な挙動はバージョンやディストリビューションによって異なるため、導入時は必ず公式ドキュメントや設定ファイルの内容を確認してください。

## 非rootユーザーでの運用とOSの自動更新

SSH鍵認証・ファイアウォールと合わせて、次の基本的な運用方針も押さえておくと安心です。

- **非rootユーザーで作業する**: 普段の操作は`sudo`権限を持つ一般ユーザーで行い、`root`での直接ログインは`PermitRootLogin no`で無効化する
- **OSのセキュリティ更新を自動化する**: `unattended-upgrades`などの仕組みで、既知の脆弱性に対するパッチが自動的に適用されるようにしておく
- **不要なサービスを動かさない**: 使っていないミドルウェアやデバッグ用のポートは閉じるか停止する

ボット自体をDocker化して運用している場合は、コンテナのログがホストのディスクを圧迫しないよう[ログローテーションと容量管理の記事](/blog/vps-disk-log-rotation/)、環境変数での秘密情報の扱いは[.env管理の基本の記事](/blog/env-secrets-management/)も参考にしてください。Dockerでのデプロイ方法自体は[ボットのDocker化の記事](/blog/bot-docker-deploy/)で詳しく扱っています。

※ここで紹介した設定項目やコマンドはディストリビューションやVPSサービスによって挙動が異なることがあります。実際に設定する際は、利用しているOS・VPSサービスの公式ドキュメントを必ず確認してください。

## まとめ

- VPSは契約した瞬間から無差別なログイン試行の対象になるため、取引所APIキーの管理とは別にOS層のセキュリティも必要
- パスワード認証はやめて、`ssh-keygen`で作成した鍵ペアによるSSH鍵認証に切り替える
- `sshd_config`で`PasswordAuthentication no`・`PermitRootLogin no`を設定する(鍵認証でログインできることを確認してから)
- `ufw`などのファイアウォールで、開けるポートをSSH(と必要な最小限のサービス)だけに絞る
- `fail2ban`で総当たり攻撃の試行を自動的にブロックし、非rootユーザーでの運用とOSの自動更新も合わせて行う

ボットのロジックや戦略の改善に比べると地味な作業ですが、VPSそのものが乗っ取られてしまえば他の対策はすべて無意味になります。運用を始める最初の段階で一度だけ整えておけば、その後は大きな手間をかけずに済む領域でもあります。
