バックテストでは問題なく動いていたロジックが、本番環境で発注した瞬間だけ `InvalidOrder` で落ちる。数量や価格の計算式自体に間違いはないはずなのに、なぜか通らない——これはボット開発でよく遭遇するつまずきの一つです。原因の多くは、取引所ごとに決められている「注文の最小単位」を無視していることにあります。この記事では、価格と数量それぞれの刻み幅、そして最小注文額という3つの制限を整理し、Pythonのccxtでどう確認・対応すればよいかを解説します。

## 「最小単位」には実は2種類ある

ひとくくりに「最小単位」と呼ばれがちですが、取引所が制限しているのは実際には別々の2つの値です。

- **価格の刻み幅(tick size)**: 注文できる価格は、取引所が決めた間隔の倍数でなければなりません。たとえば刻み幅が0.1であれば、100000.05という価格は指定できず、100000.0か100000.1のどちらかに丸める必要があります
- **数量の刻み幅(step size / ロットサイズ)**: 注文できる数量にも同様の制限があります。BTC/USDTで刻み幅が0.0001であれば、0.00012345BTCのような細かい数量は注文できません

どちらを守らなくても、プログラム側では一見「正しい数値」を渡しているように見えるため、原因の特定に時間がかかりがちな落とし穴です。

## なぜ取引所はこの制限を設けているのか

取引所がこうした刻み幅を設定する理由は、一般的にはマッチングエンジンや板(オーダーブック)の管理効率にあります。価格・数量を無制限に細かく許可すると、板に乗る注文の粒度がバラバラになり、約定処理や表示の負荷が増えてしまいます。そのため多くの取引所で、銘柄ごとに「価格はこの桁まで」「数量はこの桁まで」という上限が決められています。

板情報そのものの仕組みについては[板情報(オーダーブック)の記事](/blog/orderbook-basics/)でも解説しているので、刻み幅がどのように板の見え方に影響するかもあわせて確認すると理解が深まります。

## もう一つの制限: 最小注文額(ノーショナル)

刻み幅に加えて、多くの取引所は「1回の注文はいくら以上から」という最小注文額(ミニマムノーショナル)も設定しています。たとえば最小注文額が5USDTの取引所で、0.00001BTC(数十円相当)だけ注文しようとすると、刻み幅の条件を満たしていても最小注文額の条件で拒否されます。

この制限は、ポジションサイズの計算にも影響します。リスク管理の観点から「1トレードあたりの許容損失額」から逆算して数量を決める場合、計算結果が最小注文額を下回ってしまうケースがあり得ます。具体的な計算式は[ポジションサイズの計算式の記事](/blog/position-sizing-formula/)で解説していますので、小さい資金で運用する場合は特に注意してください。

## Pythonのccxtで確認・対応する方法

ccxtでは、各銘柄の刻み幅や最小注文額を `load_markets()` の結果から取得できます。

```python
import ccxt

exchange = ccxt.mexc({
    'apiKey': 'YOUR_API_KEY',
    'secret': 'YOUR_SECRET',
})

markets = exchange.load_markets()
market = markets['BTC/USDT']

print(market['precision'])  # 価格・数量の精度(桁数や刻み幅)
print(market['limits']['amount'])  # 数量の最小・最大
print(market['limits']['price'])   # 価格の最小・最大
print(market['limits']['cost'])    # 最小注文額(ノーショナル)
```

手計算で丸めるのではなく、ccxtが提供するヘルパー関数を使うのが安全です。取引所ごとの丸め方式(四捨五入か切り捨てかなど)の違いを吸収してくれます。

```python
symbol = 'BTC/USDT'
raw_amount = 0.0012345
raw_price = 100000.123456

amount = exchange.amount_to_precision(symbol, raw_amount)
price = exchange.price_to_precision(symbol, raw_price)

order = exchange.create_limit_buy_order(symbol, amount, price)
```

自分で `round()` を使って丸めると、取引所が採用している丸め方式と食い違い、結局 `InvalidOrder` になることがあります。可能な限り `amount_to_precision` / `price_to_precision` に処理を委ねるほうが安全です。

## よくある失敗パターン

実装でつまずきやすいポイントをまとめます。

- **`load_markets()` を一度しか呼ばずキャッシュし続ける**: 刻み幅や最小注文額は取引所側の仕様変更で変わることがあります。起動時に一度取得した値をずっと使い続けると、変更後に突然発注が失敗するようになります。定期的に再取得する、またはエラー発生時に再読み込みする仕組みを入れておくと安心です。この手の仕様変更への備え方は[取引所のAPI仕様変更に備えるボット設計の記事](/blog/exchange-api-spec-change/)で詳しく扱っています
- **浮動小数点の誤差をそのまま注文に使う**: Pythonの浮動小数点演算では `0.1 + 0.2` が `0.30000000000000004` になるような誤差が発生します。内部計算を `Decimal` で行うか、最終的に必ずccxtの精度変換関数を通すことで回避できます
- **先物(無期限先物)で `contractSize` を見落とす**: 先物では「1枚あたりの数量」が現物と異なる場合があります。現物用のロジックをそのまま先物に流用すると、意図しない数量で発注してしまうことがあるため注意が必要です
- **エラーを握りつぶして次の注文に進む**: `InvalidOrder` を単純に無視すると、本来発注されるべき注文が静かに失敗し続け、ボットが機能していないことに気づくのが遅れます。ccxtのエラーハンドリング全般については[ccxtのエラーが解決しないときの記事](/blog/ccxt-common-errors/)も参考になります

## 設計で気をつけたいポイント

- 注文を組み立てる処理の最後に、必ず `amount_to_precision` / `price_to_precision` を通す
- `load_markets()` の結果は定期的に再取得し、古いキャッシュのまま発注し続けない
- 最小注文額を下回りそうな小さいポジションサイズを計算した場合は、発注せずにスキップする分岐を入れる
- `InvalidOrder` が発生した場合は、ログに刻み幅・計算した数量・価格をすべて残し、原因調査できるようにしておく

ccxtの主要メソッドの使い方は[ccxtの使い方まとめ](/blog/ccxt-cheatsheet/)でも一覧化しているので、実装の際にあわせて参照してください。

※刻み幅や最小注文額の具体的な数値は取引所・銘柄・時期によって異なり、変更されることもあります。実装前には必ず利用する取引所の公式ドキュメントや `load_markets()` の結果で最新の値を確認してください。

## まとめ

- 取引所には価格の刻み幅(tick size)と数量の刻み幅(step size)という2種類の制限があり、どちらを無視しても注文は拒否される
- これに加えて「最小注文額(ノーショナル)」という別の制限もあり、小さすぎる注文は刻み幅を満たしていても拒否される
- これらの値はccxtの `load_markets()` で取得できるので、手計算で丸めず `amount_to_precision` / `price_to_precision` を使うのが安全
- 刻み幅や最小注文額は取引所側の仕様変更で変わることがあるため、キャッシュを定期的に更新する仕組みが必要
- `InvalidOrder` を握りつぶさず、原因がわかるログを残しておくことが運用上の安心につながる

地味な制限ですが、見落とすと本番でだけ発注が失敗するという厄介な不具合につながります。実装の早い段階でこの3つの制限を必ず確認しておきましょう。
