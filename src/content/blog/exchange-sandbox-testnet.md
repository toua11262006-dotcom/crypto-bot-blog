ボットの本番投入前に「まずは少額で試そう」と考える人は多いですが、少額とはいえ実際の資金を動かすことに変わりはありません。取引所の一部は、実際の資金を一切使わずにAPI接続そのものを検証できる**サンドボックス(テストネット)環境**を提供しています。この記事では、その仕組みと、導入時に見落とされがちな注意点を整理します。

## サンドボックスとペーパートレードは別物

「仮想の資金で試す」という点だけを見ると、[ペーパートレード](/blog/paper-trading-guide/)と似ているように思えますが、仕組みはまったく違います。

| 項目 | ペーパートレード | サンドボックス(テストネット) |
| --- | --- | --- |
| 発注の送り先 | 送らない(ボット内部で約定を模擬) | 実際に取引所のテスト用サーバーへ送信 |
| 検証できること | 戦略ロジックの判断・エントリー/決済のタイミング | API認証・リクエスト形式・レスポンス処理・エラーハンドリング |
| 板・約定の再現度 | 自前のロジック次第 | 取引所側のテスト環境の実装次第(本番と差がある場合も) |
| 必要なもの | 価格データのみ | テスト専用のAPIキー、場合によってはテスト用の口座 |

ペーパートレードは「戦略が正しく判断できているか」を検証するのに向いていますが、**「自分の書いたAPI連携コードが取引所の仕様通りに動くか」**まではカバーしません。注文パラメータの名前を間違えていても、ペーパートレードの実装次第では気づけないことがあります。

一方でサンドボックスは、実際のエンドポイントにリクエストを送るため、認証ヘッダーの組み方や必須パラメータの欠落など、**本番に投入して初めて気づくような接続まわりの不備**を事前に洗い出せます。両者は役割が違うので、本来は両方を組み合わせて検証するのが理想です。

## どんな場面でサンドボックスが役に立つか

- 新しい取引所に対応するコードを書くとき、本番資金を使わずに認証・発注・キャンセルの一連の流れを確認したい
- [取引所側のAPI仕様変更](/blog/exchange-api-spec-change/)があった後、本番に反映する前に差分を確認したい
- CI上で自動テストを回したいが、本番APIを叩くとレートリミットや実際の注文が発生してしまい都合が悪い

特に「新しい取引所への対応」や「大きめのロジック変更」をするときは、本番の口座でいきなり試すよりもリスクを抑えて検証できます。

## ccxtでのサンドボックスモードの切り替え

`ccxt`を使っている場合、多くの取引所クラスには`set_sandbox_mode()`というメソッドが用意されています。これを使うと、接続先のベースURLをテスト用のエンドポイントに切り替えられます。

```python
import ccxt

exchange = ccxt.mexc({
    'apiKey': 'YOUR_TESTNET_API_KEY',
    'secret': 'YOUR_TESTNET_SECRET',
})

# サポートされている取引所ではテスト環境に切り替わる
exchange.set_sandbox_mode(True)

markets = exchange.load_markets()
order = exchange.create_order('BTC/USDT', 'limit', 'buy', 0.001, 20000)
print(order)
```

ここで重要なのは、**`set_sandbox_mode(True)`が全ての取引所で使えるわけではない**という点です。取引所によっては

- サンドボックス自体を提供していない
- 提供していても`ccxt`側がまだ対応していない
- テスト環境用に別途、専用のAPIキー発行や申請が必要

といったケースがあります。対応状況は`ccxt`のバージョンや取引所の仕様変更によって変わるため、**使う前に必ず公式ドキュメントと`ccxt`のドキュメントで最新の対応状況を確認してください**。

## サンドボックスを使う上での3つの注意点

### 1. 本番環境と仕様が完全に一致するとは限らない

テスト環境は本番と同じ仕様を目指して作られていますが、運用上の理由で**更新のタイミングがずれる**ことがあります。「サンドボックスで通ったから本番でも確実に動く」と過信せず、最終的には本番環境で少額の実注文を使った確認も行うのが安全です。

### 2. 板の厚みや約定の再現度は限定的

テスト環境は実際の市場参加者が少ないため、約定価格や[スリッページ](/blog/slippage-thin-orderbook/)の挙動が本番と大きく異なることがあります。サンドボックスは「APIとして正しく動くか」を見るための場であり、「本番でどう約定するか」を検証する場ではないと割り切っておくとよいでしょう。

### 3. テスト用キーと本番用キーを厳格に分ける

テスト用のAPIキーと本番用のAPIキーを同じ[環境変数管理](/blog/env-secrets-management/)の仕組みで扱っていると、設定ミスで本番用のつもりがテスト環境に接続していた(あるいはその逆)という事故が起きがちです。環境ごとに変数名やコンフィグファイルを明確に分け、どちらに接続しているかをログの先頭に必ず出力する習慣をつけておくと安全です。[APIキーの安全管理](/blog/api-key-security/)の考え方とあわせて運用ルールを決めておきましょう。

## まとめ

- サンドボックス(テストネット)は、仮想資金で**実際のAPIエンドポイント**に接続して検証できる環境で、ボット内部で約定を模擬する[ペーパートレード](/blog/paper-trading-guide/)とは目的が異なる
- 新しい取引所への対応やAPI仕様変更後の確認など、**接続まわりの不備**を本番資金を使わずに洗い出すのに向いている
- `ccxt`では`set_sandbox_mode()`で切り替えられる取引所もあるが、対応状況は取引所・バージョンによって異なるため必ず公式情報を確認する
- 板の薄さなど本番と異なる部分もあるため、サンドボックスでの検証はあくまで「API接続の確認」と位置づけ、最終確認は少額の本番取引で行う
- テスト用キーと本番用キーの取り違えを防ぐ運用ルールを事前に決めておく
