自動売買ボットを本番で動かしていると、「新しいロジックを入れたら、想定外の動きをしている」という場面に必ず遭遇します。こうしたとき、落ち着いて前のバージョンに戻せるかどうかは、事前にどれだけ準備しておいたかで大きく差が出ます。この記事では、ボットのバージョン管理とロールバックの基本的な考え方を整理します。

## なぜボットには「戻す」仕組みが特に重要なのか

一般的なWebアプリの不具合は、気づくまでに多少の時間がかかっても大きな問題にならないことが多いです。一方で取引ボットの不具合は、気づくのが遅れるほど不要な発注や想定外のポジションが積み重なっていく可能性があります。

そのため、取引ボットの運用では次の2点を分けて考える必要があります。

- **検知**: 不具合にどれだけ早く気づけるか
- **復旧**: 気づいたあと、どれだけ早く・安全に前の状態へ戻せるか

検知の仕組みについては[毎日の監視ルーティンの記事](/blog/bot-daily-monitoring-routine/)や[Discordへの通知ボットの記事](/blog/discord-notification-bot/)で扱っているので、本記事では「戻す」側に絞って解説します。

## バージョンを追跡可能にする

ロールバックは「どのバージョンが正常だったか」を特定できることが前提になります。そのための基本がGitのタグ付けです。

```bash
# 動作確認が取れた時点でタグを打つ
git tag -a v1.3.0 -m "グリッド幅の計算ロジックを修正"
git push origin v1.3.0
```

セマンティックバージョニング(`メジャー.マイナー.パッチ`)に厳密に従う必要はありませんが、少なくとも「いつ・何を変えたか」が後から追えるように、タグとCHANGELOGは最低限整備しておくと安心です。

```markdown
## v1.3.0 (2026-11-20)
- 修正: グリッド幅の計算が板の最小刻みを考慮していなかった不具合
- 変更: 発注間隔のデフォルト値を調整
```

## Dockerイメージのタグをバージョンに紐付ける

[Docker化の記事](/blog/bot-docker-deploy/)で触れたとおり、ボットをコンテナ化している場合は、イメージのタグとGitのタグを一致させておくと切り戻しが単純になります。

```bash
docker build -t my-bot:v1.3.0 .
docker push myregistry/my-bot:v1.3.0
```

`latest` タグだけで運用していると、「今動いているのがどのバージョンか」が分からなくなりがちです。本番で使うタグは必ずバージョン番号で固定し、`latest` は開発用途に留めるのが基本的な考え方です。

[GitHub Actionsでの自動デプロイの記事](/blog/github-actions-bot-deploy/)で紹介したCI/CDと組み合わせれば、タグをpushした瞬間に該当バージョンのイメージがビルド・公開される仕組みを作れます。

## ロールバックすべきかどうかの判断

不具合に気づいたとき、まず考えるべきは「ロールバックするか、その場で修正するか」の判断です。一般的には次のような基準で考えられます。

| 状況 | 対応の方向性 |
| --- | --- |
| ポジションや注文に影響する可能性がある | 原因調査より先にボットを停止し、必要ならロールバック |
| 表示・ログなど実取引に影響しない部分の不具合 | 落ち着いて原因を特定してから対応を決める |
| 修正内容が単純で影響範囲が明確 | 前方修正(fix forward)の方が早いこともある |
| 原因がすぐに特定できない | 迷わず直前の正常バージョンへ戻す |

どのパターンでも共通するのは、「原因が分かるまでボットを動かし続けない」という判断です。ボットを止める基準については[停止タイミングの記事](/blog/bot-stop-criteria/)で詳しく扱っています。

## ロールバックの実行手順

Dockerとタグ管理をしている前提で、実際の切り戻しは次のような流れになります。

1. **ボットを安全に停止する**(新規発注を止め、既存注文の扱いを確認する)
2. **前のバージョンのイメージを起動する**
   ```bash
   docker stop my-bot
   docker run -d --name my-bot myregistry/my-bot:v1.2.4
   ```
3. **状態の復旧を確認する**(ポジション・未決注文・内部状態が想定と一致しているか)
4. **ログと通知を確認し、正常に稼働しているかを見る**

手順3の「状態の復旧」は特に見落としやすいポイントです。ボットが内部的にポジションや注文履歴をローカルに保持している場合、イメージを戻しただけでは状態がずれることがあります。再起動時の状態復旧については[再起動時の状態復旧の記事](/blog/bot-restart-state-recovery/)で詳しく整理しているので、ロールバック前に見直しておくと安全です。

## ロールバック後にやること

切り戻して終わりにせず、次のことを必ず行っておくと再発防止につながります。

- **原因の記録**: CHANGELOGやIssueに「何が起きて、なぜ戻したか」を残す
- **再現の確認**: 可能であればテスト環境で同じ不具合を再現し、修正を検証する
- **監視項目の見直し**: 今回の不具合をもっと早く検知できる監視項目がなかったかを振り返る

テストの整備については[pytestでのテストの記事](/blog/bot-testing-pytest/)も参考になります。ロールバックを何度も繰り返すような状況であれば、本番投入前の検証プロセス自体を見直すサインとも言えます。

## まとめ

- 取引ボットは不具合の発覚が遅れるほどリスクが積み重なるため、「戻す」仕組みを事前に用意しておくことが重要
- Gitのタグ・CHANGELOG・Dockerイメージのタグを一致させておくと、どのバージョンが正常だったかを後から追いやすい
- 不具合に気づいたら、まず「ロールバックか前方修正か」を判断し、迷ったら直前の正常バージョンへ戻すのが基本
- ロールバック後はポジション・注文などの状態が想定と一致しているかを必ず確認する
- 切り戻して終わりにせず、原因の記録と再発防止につなげる
