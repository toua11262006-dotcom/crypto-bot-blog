自動売買ボットのバグというと「取引しなくなる」事故を想像しがちですが、実はもっと怖いのは**意図しない注文が通ってしまう**事故です。ロジックのバグ、APIの再接続による二重送信、変数の桁違いなど、原因はさまざまでも結果は同じ「おかしな注文が取引所に送られる」こと。これを防ぐ最後の壁が、発注直前に挟む「発注前チェック(プレトレードバリデーション)」です。

## サーキットブレーカーだけでは足りない理由

[資金管理の記事](/blog/bot-risk-management/)で紹介したサーキットブレーカーは、**損失が一定額を超えたら取引を止める**仕組みです。これはとても重要ですが、あくまで「結果」に反応する仕組みであり、注文そのものがおかしいかどうかは見ていません。

一方で発注前チェックは、**注文を送る直前にその注文自体の妥当性を検証する**仕組みです。両者は役割が違うので、片方だけでは守りが不完全になります。

- サーキットブレーカー: 「損失が出た後」に止める(事後対応)
- 発注前チェック: 「おかしな注文を送る前」に止める(事前対応)

どちらも実装してこそ、守りに抜け穴がなくなります。

## 誤発注が起きる典型的なパターン

実際に事故につながりやすいのは、派手な相場変動よりも地味なロジックの不備です。

- 計算式のバグで注文数量が想定の10倍や100倍になる
- API接続が切れて再送したところ、実は先の注文も通っていて二重発注になる
- 取引所側の仕様変更で、数量や価格の「刻み幅」が変わり丸め誤差が異常な値になる([ロットサイズの記事](/blog/order-precision-lot-size/)で詳しく解説)
- テスト用のパラメータ(極端に大きい数量など)を本番コードに残したまま動かしてしまう
- 残高を正しく参照できず、実際にはない資金で発注しようとする

これらはどれも「ロジックは一見正しく動いている」ように見えるため、ログを目で見て気づくのは簡単ではありません。だからこそ、機械的なチェックをコードに組み込む必要があります。

## チェック1: 数量の絶対的な上限・下限

まず最もシンプルで効果が大きいのが、**注文数量に絶対的な上限値を設定する**ことです。戦略ロジックがどんな計算をしても、この上限を超える注文は物理的に送信しない、という最後の防波堤を用意します。

上限は「通常の発注サイズの数倍」程度に設定しておくと、正常な取引を妨げずに異常値だけを弾けます。下限についても、取引所の最小注文単位を下回る注文は意味がないので同様にチェックします。

## チェック2: 価格の妥当性チェック(異常値フィルタ)

成行注文でも、約定前に現在値と比較して**価格が一定range内かどうか**を確認します。たとえば直前の参照価格から数%以上離れた価格で注文を出そうとしている場合、何らかの異常(データの取得失敗、計算ミスなど)が起きている可能性が高いため、送信前に止めて通知する設計が安全です。

限定注文(リミット)の場合は、指定した価格そのものが現在の板からかけ離れていないかを見るだけでも、桁違いの入力ミスを防げます。

## チェック3: 重複注文の防止

API接続の切断・再接続や、タイムアウト後のリトライは珍しくありません。[取引所の障害対応の記事](/blog/exchange-outage-failsafe/)でも触れていますが、**「送信したつもりだが結果が受け取れなかった」**状況で安易に再送すると、二重発注につながります。

対策として、注文ごとに一意のクライアント注文ID(idempotency key)を発行し、同じIDでの再送はサーバー側で重複として扱われるようにする、あるいは自前で「送信済みID」を記録しておき、同一注文を再送しない仕組みを入れます。ccxtを使う場合は取引所がclientOrderId相当のパラメータに対応しているか確認しておくとよいでしょう([ccxtのよくあるエラー](/blog/ccxt-common-errors/)も参考になります)。

## チェック4: 残高・ポジションとの整合性

発注前に、**手元で把握している残高・ポジション情報と、これから出す注文が矛盾していないか**を確認します。たとえば「保有していないはずの量を売却しようとしている」「資金を超える量を買おうとしている」といった注文は、計算ロジックのどこかにバグがある証拠です。

このチェックのために、ボット内部では定期的に取引所から残高を取得して自前の状態と突き合わせる処理を持っておくと、ズレにも早く気づけます。[ボットが休眠していた失敗談](/blog/bot-dormant-bug-story/)のように、状態のズレは静かに進行することが多いので注意が必要です。

## チェック5: 取引所の精度・最小ロットへの適合

数量や価格は、取引所ごとに決められた「刻み幅」に丸めてから送信する必要があります。丸め処理そのものにバグがあると、本来より大きい数量に化けてしまうことがあるため、丸めた後の値にも上限チェックを通すのが安全です。詳しい仕組みは[ロットサイズの記事](/blog/order-precision-lot-size/)にまとめています。

## 実装イメージ: 発注前チェックをまとめたラッパー

5つのチェックは、注文を送る関数の前段にまとめて配置すると管理しやすくなります。簡単なイメージは以下の通りです。

```python
class OrderValidationError(Exception):
    pass


def validate_order(order, account_state, max_qty, price_ref, price_tolerance_pct):
    # チェック1: 数量の絶対上限
    if order["amount"] <= 0 or order["amount"] > max_qty:
        raise OrderValidationError(f"数量が異常です: {order['amount']}")

    # チェック2: 価格の妥当性
    if order.get("price"):
        diff_pct = abs(order["price"] - price_ref) / price_ref * 100
        if diff_pct > price_tolerance_pct:
            raise OrderValidationError(f"価格が現在値から{diff_pct:.1f}%離れています")

    # チェック3: 重複注文
    if order["client_order_id"] in account_state.sent_order_ids:
        raise OrderValidationError("同一IDの注文が送信済みです")

    # チェック4: 残高・ポジションとの整合性
    if order["side"] == "sell" and order["amount"] > account_state.position_qty:
        raise OrderValidationError("保有量を超える売却注文です")
    if order["side"] == "buy" and order["cost"] > account_state.available_balance:
        raise OrderValidationError("利用可能残高を超える買い注文です")

    return True


def place_order_safely(exchange, order, account_state, max_qty, price_ref, price_tolerance_pct):
    validate_order(order, account_state, max_qty, price_ref, price_tolerance_pct)
    result = exchange.create_order(**order)
    account_state.sent_order_ids.add(order["client_order_id"])
    return result
```

ポイントは、`validate_order` を**発注関数と分離して、単体テストしやすい形にしておく**ことです。異常なロジックの出力をテストケースとして用意し、正しく例外が発生するかを確認できます。[ボットのテストの記事](/blog/bot-testing-pytest/)で紹介したpytestの考え方と組み合わせると、発注前チェックの網も検証できます。

## まとめ

- サーキットブレーカーは「損失が出た後」の対応、発注前チェックは「注文を送る前」の対応で役割が異なる
- 誤発注は計算ミス・二重送信・丸め誤差・残高ズレなど、地味な原因から起きやすい
- 数量の絶対上限、価格の妥当性、重複防止、残高整合性、精度適合の5つを発注関数の前段で機械的にチェックする
- チェック処理は発注処理と分離し、単体テストできる形にしておくと安心して運用できる

守りの仕組みは地味で、うまく機能しているときほど「何も起きなかった」という結果にしかなりません。しかしそれこそが、ボットを長く安全に動かし続けるための土台になります。
